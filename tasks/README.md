# Nobody-Blog · 任务管理目录

本目录用于管理 `Nobody-Blog` 的开发任务、验收标准与执行记录。它不是网站文章目录；**博客文章存放在 `hexo-core/source/_posts/`，此处的 Markdown 不应参与 Hexo 站点内容生成。**

## 1. 目录约定

```text
tasks/
├── README.md                                   # 本说明：任务管理规则
├── ...                                         # 后续未完成任务
└── completed_tasks/                            # 完成并通过验收的历史任务
    └── 01_HEXO_MIGRATION_REPAIR_AND_VALIDATION.md
```

- **`tasks/` 根目录**：只放 `TODO`、`IN_PROGRESS`、`BLOCKED` 或待复验的任务文档，以及本 README。
- **`tasks/completed_tasks/`**：只存放已经实施、经过验收、状态为 `COMPLETED` 的任务文档；保留完整任务要求与最终记录，不要在归档时删除测试证据。
- **`_design_backup/`**：原静态网页设计备份，是视觉/交互参考，不是任务归档目录。
- **`hexo-core/`**：Hexo 的实际构建、模板和内容所在目录。执行 Hexo 命令前通常需要先 `cd hexo-core`。

如果 `completed_tasks/` 为空，可创建目录并用 `.gitkeep` 保持在 Git 中；**不要求为它额外建立一份 Markdown README**。

## 2. 命名与状态

任务文件建议采用以下格式：

```text
NN_SHORT_TASK_NAME.md
```

例如：`01_HEXO_MIGRATION_REPAIR_AND_VALIDATION.md`。同一任务的记录尽量持续更新在该文件内，避免出现 `task-final.md`、`task-final2.md` 等难以追踪的副本。后续如需划分更细的任务，可以使用 `02_...md`、`03_...md`；编号表示任务顺序，**不等于已经完成**。

状态定义：

| 状态 | 含义 | 存放位置 |
|---|---|---|
| `TODO` | 已制定要求，尚未开始实施 | `tasks/` |
| `IN_PROGRESS` | 正在修改或测试 | `tasks/` |
| `BLOCKED` | 存在未解决的阻塞问题或缺少关键验收能力 | `tasks/` |
| `COMPLETED` | 实施完成，全部阻断性验收通过并有真实记录 | `tasks/completed_tasks/` |

**“代码看起来写完了”“能够成功编译”“Codex 声称已修复”均不自动等于完成。**只有达到该任务文件自身的验收标准才可归档。

## 3. Codex 执行流程

1. **读取任务**：先读本 README，再读指定任务文件，查看当前仓库真实代码与 `git status`。不要用文档中的旧快照描述覆盖现有事实。
2. **建立基线**：确认环境、相关源代码和已有功能，运行可执行的基线测试，记录复现情况。保护现有未提交修改、文章及设计备份。
3. **实施修复**：按任务步骤逐项修改；优先做局部、可审查的改动，保留既有架构及用户指定的设计约束。
4. **执行测试**：运行构建、自动化检查和必要的浏览器验证。每项验收用 `PASS` / `FAIL` / `NOT RUN` 记录，并附上命令、结果、测试环境与必要的复测步骤。
5. **回写记录**：在**同一份任务文件**的执行记录区写入修复清单、涉及文件、测试结果、未解决的问题；不要只在聊天回复里汇报。
6. **归档或保留**：全部阻断项 `PASS` 后标为 `COMPLETED`，移至 `completed_tasks/`；如果有 `FAIL` / `NOT RUN`，保留原位置并标记 `IN_PROGRESS` 或 `BLOCKED`，说明下一步。
7. **向用户汇报**：用简明的“做了什么、如何验证、还有什么未完成、是否归档”结束本轮执行。

### 归档操作示例

在确认完成条件后，从仓库根目录执行：

```bash
mkdir -p tasks/completed_tasks
mv tasks/01_HEXO_MIGRATION_REPAIR_AND_VALIDATION.md tasks/completed_tasks/
```

Windows PowerShell 等环境使用对应的移动命令即可。归档后建议在涉及的后续任务里引用该文件的新路径；**不要同时保留两份同名活动任务**。历史任务文档若已存在，须先核对它确实完成和验收，再移动；不能仅因文件年代较早就归档。

## 5. 执行与证据原则

- **事实优先**：任务文件的“现存问题”是待复现线索，实际执行要以当前源代码和测试结果为准。
- **不虚报通过**：无法启动浏览器、访问外网或运行某种测试时应注明原因，保留 `NOT RUN`；不得用静态构建成功代替 UI 交互验收。
- **不破坏用户数据**：不得擅自删除原始设计、现有文章、未提交工作；不得使用破坏性 Git 命令或私自部署。
- **可追溯**：任务的约束、修复方式、测试证据和延期事项应在文档中闭环。任务完成后移动原文件而非删掉历史。
- **范围清晰**：不在当前阶段偷偷展开新需求。新增问题按严重程度纳入本任务缺陷记录，或拆成新的独立任务。
